# jPipe VS Code Extension — CLAUDE.md

## Project Overview

This is a VS Code extension and Language Server for **jPipe**, a DSL for justification modeling (used in software certification contexts at McMaster University / McSCert). Users write `.jd` files describing justification structures; the extension provides syntax highlighting, validation, completions, and diagram preview/export.

**Stack:** TypeScript, Langium 4.3 (language framework), Vitest (tests), esbuild (extension bundler), vsce (publishing).

## Language Grammar Summary

The grammar (`packages/language/src/jpipe.langium`) defines:

| Concept | Keyword | Notes |
|---|---|---|
| **Justification** | `justification Name implements Template?` | Concrete model |
| **Template** | `template Name implements Template?` | Abstract/reusable structure |
| **Evidence** | `evidence name is "label"` | Leaf node |
| **Strategy** | `strategy name is "label"` | Must be supported by ≥1 evidence/sub-conclusion |
| **SubConclusion** | `sub-conclusion name is "label"` | Intermediate conclusion |
| **Conclusion** | `conclusion name is "label"` | Root; must be supported by ≥1 strategy |
| **AbstractSupport** | `@support name is "label"` | Like abstract method; only in templates |
| **Relation** | `from supports to` | Directed support edge |
| **Load** | `load "path/to/file.jd"` | Import another `.jd` file; the path may be a glob (see below) |
| **Composition** | `composition { ... }` | Assembles/refines models with operators |

Inheritance: both justifications and templates may `implements` a parent template. `getAllElements` traverses the chain.

## Key Design Decisions

Language-level decisions live here. **Structural** decisions — packaging, boundaries, build,
release — live in [`docs/adr/`](docs/adr/README.md) and are not repeated in this file.

### @support = abstract elements
`@support` in a template is like an abstract method: justifications implementing the template **must** override every `@support` element with an `evidence` or `sub-conclusion` (type-checked). Regular (non-@support) elements are optional overrides.

### Import resolution
`JpipeImportService` does a BFS over `load` edges. Direct imports must appear in the root document; transitive imports are followed freely. Resolution is path-based (no workspace index for imports).

### Glob patterns in `load` follow **Java NIO**, not minimatch
A `load` path containing `*`, `?`, `[` or `{` is a pattern. The compiler expands it with
`FileSystems.getDefault().getPathMatcher("glob:" + pattern)` (see its `LoadResolver.java` and jpipe-compiler ADR-0022), so `jpipe-glob.ts` is a port of OpenJDK's `Globs.toUnixRegexPattern` and **must stay faithful to it** — the IDE and the compiler have to agree on which files a model loads. Recorded as jpipe-vscode ADR-VSC-0007.

The trap: `minimatch`/`picomatch` treat `**` as special only when it is a whole path segment, so they would read `models/**.jd` as `models/*.jd` and miss nested files. Under Java, `models/**.jd` matches *every* depth including the top level, while `models/**/*.jd` matches nested files only. If you touch the matcher, re-run `test/glob-matcher.test.ts`, whose cases are ported from the compiler's own `LoadResolverGlobTest`.

**Anchoring** (`anchorGlob`): a pattern is split at the last `/` before its first wildcard *character*. The literal prefix is resolved like a literal load path — so a pattern may climb out of the declaring file's directory (`../library/*.jd`) or be absolute — and the remainder is matched relative to that anchor, which is also the only subtree walked. Cutting before the wildcard character rather than at a segment boundary is what keeps `{foo/bar,baz}/*.jd` intact. Anchoring is meaning-preserving for descending patterns.

Four failure modes are errors, worded exactly as the compiler words them: malformed pattern, a `..` surviving anchoring (it follows a wildcard, so a downward walk can never satisfy it), an anchor that is not a directory, and zero matches. A load resolving to its own file is reported as `Circular load detected`. Results are sorted. Expansion prunes `node_modules`, `out`, `.git` and dot-directories (the compiler does not, but it runs once per build whereas this runs while the user types), and is memoised, with `DocumentBuilder.onUpdate` clearing the cache.

`load` glob resolution deliberately powers hover but **not** go-to-definition: F12 on a pattern returns nothing, because "go to definition" names one target and a pattern does not. The hover lists the matches as clickable links instead.

### Completion scoping
The `JpipeCompletionProvider` deliberately never falls through to Langium's global workspace index for `JustificationElement` or `Template` references — it restricts candidates to local + explicitly loaded files only. The one exception is `implements` in the `parentTemplateCandidateDescriptions` method, which does consult the workspace index and can auto-insert a `load` statement.

### Image generation
`ImageGenerator` shells out to an external **jPipe CLI** (default: `jpipe` on PATH) or a **JAR file**. The extension does not bundle the compiler. Configure via:
- `jpipe.cliPath` (takes priority)
- `jpipe.jarFile` + `jpipe.setJavaVersion`

Exit codes: `1` = model has errors, `42` = compiler crashed.

### Required versions
`src/extension/requirements.ts` names the **oldest** compiler, jpipe-runner and Python this release works with, and no newest (jpipe-vscode ADR-VSC-0032). A compiler below the minimum is refused before any run, with an update offered; the managed install lists only releases at or above it. Raising a minimum is a user-facing change: changelog entry, and the Marketplace README's "Required software" (held by `test/requirements.test.ts`). Pylance is a soft dependency — never add it to `extensionDependencies` or `extensionPack`.

## Build & Dev Workflow

```bash
# First time / dependency install
npm install
npm install -g @vscode/vsce          # for packaging

# Regenerate AST/grammar from jpipe.langium (run after any grammar change)
npm run langium:generate

# Full build
npm run build

# Watch mode
npm run watch

# Run in VS Code (launches Extension Development Host)
# → press F5 in VS Code

# Tests (Vitest, both packages)
npm test

# Package the extension as a .vsix (CI names its artefact jpipe-extension.vsix)
cd packages/extension
vsce package -o jpipe-vscode.vsix

# Install locally
code --install-extension jpipe-vscode.vsix

# Publish to marketplace
vsce publish
```

**Important:** The files under `packages/language/src/generated/` are generated artifacts. Always re-run `npm run langium:generate` after editing `jpipe.langium`.

## Branches and pull requests

This repository follows the jPipe workflow in the organisation's [contributing guide](https://github.com/jpipe-mcscert/.github/blob/main/CONTRIBUTING.md), including its rules for AI assistants: `main` holds releases, `dev` is the integration and default branch, work branches are cut from `dev` and return to it by pull request (jpipe-vscode ADR-VSC-0030). What is specific here:

- **CI:** `build.yml` (job `build`) runs on pushes to `main` and `dev` and on every pull request; `sonar.yml` (job `Build and analyze`, SonarQube Cloud with the gate waited on) runs on every pull request and on pushes to `main`. Both jobs are required checks on `main`; the README's "What has to be green before a pull request merges?" has the details, including why pull requests from forks cannot be analysed.
- **Releases:** `scripts/release.sh prepare X.Y.Z` runs on a work branch cut from `dev` (it refuses `main` and `dev`); that branch goes into `dev` by pull request, then `dev` into `main` by the release pull request. A maintainer then runs `scripts/release.sh preflight X.Y.Z` on `main` and pushes the `vX.Y.Z` tag, which `release.yml` turns into a GitHub Release and a Marketplace publish — it refuses a tag that is not on `main`. A hotfix is prepared with `prepare --hotfix X.Y.Z` on a fix branch cut from `main`, and goes into `main` by its own pull request. See "How to cut a release?" in the README and jpipe-vscode ADR-VSC-0008.

## Changelog Maintenance

`CHANGELOG.md` is the source of truth for what shipped in each version. **Keep it current: write the entry in the change that makes it, not at release time.**

- Every user-facing change (feature, bug fix, or documentation) must have a corresponding entry by the time it is merged into `dev`.
- Accumulate changes under a top `### vX.Y.Z (Unreleased)` heading while work is in flight. Closing the section out is `scripts/release.sh prepare X.Y.Z`'s job — don't date the heading by hand.
- Follow the existing structure: `Leader:` line, then `Features:` / `Bug Fixes:` / `Documentation:` sub-lists. Prefix each item with the affected area in bold (e.g. **Language Server:**, **Extension:**, **Grammar:**, **CI/CD:**). Reference the closed issue/PR where relevant.
- The version lives in **four** places that must agree — the three `package.json` files (root, `packages/extension`, `packages/language`) *and* the `jpipe-language` dependency inside `packages/extension/package.json`. `scripts/release.sh prepare` sets all four and reconciles the lockfile; see "How to cut a release?" in the README for why doing it by hand is fiddly.
- SemVer: new capability → minor bump; fixes/docs only → patch bump.

**Editorial style — write for users, not developers.** The changelog is read by people using the extension, not by contributors. Each entry should describe *what changed for the user* and *why it helps*, in plain language:

- Lead with the benefit or the observable behaviour, not the mechanism. "Let the extension fetch and update the compiler for you" beats "Add managed compiler mode via `installFromRelease`".
- Avoid internal jargon: no setting IDs (`jpipe.executionMode`), command IDs, method names, class names, or file paths in the entry text. Refer to features by their user-facing name ("execution mode setting", "Export command").
- Use a short bold lead-in that names the capability in user terms (e.g. **No-install setup:**, **One-click export:**), then a sentence of plain explanation.
- Keep it concrete and honest — say what a user can now do, and call out who benefits (e.g. "especially handy on Windows"). Reference the closed issue/PR in parentheses.
- Roll several related commits into one readable bullet rather than mirroring the git history one-to-one.

To reconstruct entries from history, mine `git log <last-tag>..HEAD` and group by merged PR — then translate the technical commit messages into user-facing prose per the style above.

## Testing

Both packages use Vitest. `npm test` at the root runs both, and CI runs it between build and
packaging, so a red suite blocks the VSIX.

### `packages/language/test/`

28 files, integration-style: they import `'jpipe-language'`, which resolves through the package's
`exports` map to the **built** `out/index.js`, and drive the LSP through Langium's test helpers.
`parsing.test.ts`, `linking.test.ts` and `validating.test.ts` are the core three; the rest cover
completion, code actions, renaming, globs, layout, hovering, symbols and semantic tokens.

**Consequence: `packages/language/out/` must exist before these run.** Every CI job and
`release.sh check_build` therefore run `langium:generate → build` before `test`, in that order.

The parsing test's `beforeAll` wires up services with `EmptyFileSystem` (no real disk). For import-heavy tests, prefer constructing multi-document scenarios manually via `JpipeImportService.parseDocumentFromPath`. Note that `JpipeImportService` reads through `node:fs` rather than Langium's `FileSystemProvider`, so `EmptyFileSystem` does *not* intercept it — `load`-related tests write real files to a temp dir (see `import.test.ts`, `glob-load.test.ts`).

### `packages/extension/test/`

**There is no VS Code host here**, so a module that imports `vscode` cannot be loaded. Testable
logic therefore lives in vscode-free modules that the vscode-importing ones consume:

- `process-launcher.ts` — Windows command resolution and `cmd.exe` escaping, and `execFileText`,
  which decodes a program's output itself (VS Code 1.139+ can break `setEncoding`). Platform, env and
  filesystem are injected, so the Windows rules are exercised on any runner.
- `release-selection.ts` — semver precedence, release filtering, download host allowlist.

When adding extension logic worth testing, put it in such a module rather than reaching for
mocks of the VS Code API. Anything that genuinely needs the editor (decorations, menu
`when`-clauses, commands) has **no** automated coverage today and must be checked by hand in the
Extension Development Host; closing that gap would mean adopting `@vscode/test-cli`. That
trade-off — and the list of modules it leaves uncovered — is recorded in jpipe-vscode
ADR-VSC-0004.

Settings groups are titled `jPipe › <Tool> › <Group>` (`Compiler` or `Runner`, each starting with `General`), because VS Code has one level of groups; a new group follows it (ADR-VSC-0028, held by `test/settings.test.ts`). Setting identifiers never change with a group's title.

The **Models view** (`jpipe.models`, in the `jpipe` activity-bar container) is built from
*standard* LSP requests only — `workspace/symbol` (templates are `Interface`, justifications
`Class`), `typeHierarchy/subtypes` per template, and `textDocument/prepareCallHierarchy` per model
(a composition's item has its operator as `detail`) then `callHierarchy/outgoingCalls` per
composition (its operands) — so it needs no custom protocol. Its Errors
group (an overlay) comes from the client's own diagnostics, and its Excluded group (a partition)
from `ExclusionManager`; changes to either regroup without a server round trip. The activity
is always shown, even in a workspace with no `.jd` file, because it is where a first model is
created; opening it activates the extension. With no model, the Models view shows its welcome
text (`viewsWelcome`) and the Outline and Libraries views are hidden (`jpipe.noModels`). The `jpipe.activated` context key only hides the
palette commands that need a model or a library to act on.

Right-clicking a model offers the same three entries, directly in the menu, in the editor, on a
`.jd` file in the Explorer, and on a Models row: Open Diagram Preview, the `jpipe.exportAs` submenu
(the only place export formats are listed), and Exclude/Include (ADR-VSC-0027, held by
`test/menus.test.ts`). Their commands therefore take a tree node, an Explorer URI or nothing, and
resolve it to a model (`targetOf` in `commands.ts`).

The preview panel auto-refreshes on file save, highlights the node under the cursor (via LSP `textDocument/documentSymbol`), and has zoom controls (+/−/0 keys or toolbar buttons).

The **Run panel** is a second webview, opened by every ▶ and ✓ and never by opening a file (a check
imports the libraries). It shows the last run only — the runner's dataflow SVG (`--dataflow` on
jpipe-runner 4.0.x, `--diagram` on every later or unknown release, chosen by `dataflowFlag`; the
report's `dataflow` in schema 1, `diagram` in schema 2; the argument-only view is left to the preview), under a bar that says *Execution* or *Check · no step
called* first. It shares that run with the Results view through `RunSession`, and the two come
forward together; until a report arrives Results lists one status row, and, with jpipe-runner 4.1 or
later, the elements as their events decide them, while the verdict bar counts them (ADR-VSC-0033). A node click lights it and
everything downstream (walked from the SVG's edge titles, `webview/flow.ts`) and selects an
element's row in Results; a second click, the background or Escape clears; a double-click opens
the element. A runner that cannot draw (Graphviz
missing, exit 4, no report) is launched once more without the drawing (ADR-VSC-0031).

## Code Conventions

- All source is TypeScript (ES modules, `"type": "module"`), targeting Node 22.
- The extension bundle is CJS (esbuild converts it); the language server stays ESM.
- Langium services are wired via constructor injection; access shared services through the injected `JpipeServices` handle, not via global imports.
- AST node type guards (`isJustification`, `isTemplate`, etc.) come from `./generated/ast.js` — use them instead of `instanceof` or `.$type` comparisons.
- Prefer `getAllElements` (includes inherited chain) over `getLocalElements` (only directly declared) unless you explicitly want only local elements.
